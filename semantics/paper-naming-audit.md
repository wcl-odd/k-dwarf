# Paper Naming and Implementation Audit

This audit relates the current Chapter 3 to the current K sources. It makes **no identifier, rule, interface, or paper changes**. Its primary references are §3.3, Evaluation Semantics (paper reference, not required to run this artifact) and §3.4, Location Descriptions (paper reference, not required to run this artifact), with §3.1 (paper reference, not required to run this artifact), §3.2 (paper reference, not required to run this artifact), and the abridged K example in §3.5 (paper reference, not required to run this artifact). Current source identities and validation scope are recorded in the optional output/ package. Paper source files are not required to run this repository. Line references below address the unchanged executable definitions; comment translation preserves line numbers.

The classifications are **matching name**, **different name, corresponding role**, **paper abbreviation**, and **implementation mechanism not displayed**. A corresponding role is not a proof of semantic equivalence. Substantive differences are listed separately below. Mathematical notation is transcribed in plain text where that makes the correspondence easier to read.

The file links below follow the current `domains/`, `frontend/`, and `execution/` layout. Only `requires` paths changed during that reorganization; definition line numbers, source spellings, module names, and stable KAST names remain the same. The unused `DWARF-FAILURES` compatibility module is not part of the current definition.

## Definition and Scope Differences Left Unchanged

These are review findings, **not proposed or completed semantic changes**. The audit is not an exhaustive equivalence proof or a new validation run.

1. **Memory-result typing and normalization.** §3.4 requires an integer/generic top and computes `bits(a,A)`. Current `[Memory]` accepts `val(N,_)` and returns raw N, without that type guard or address normalization. A negative or wider-than-address representative is therefore preserved. Fragment memory descriptions also retain N. See [core.k](execution/core.k), lines 417–422, and [composition.k](execution/composition.k), lines 39–44.
2. **Conditional-branch typing.** §3.3 requires an integer/generic condition. `[BraTrue]` and `[BraFalse]` match any carried type and test the raw integer representative for nonzero/zero, without `integerType`. This includes floating-point carriers if supplied by prior computation. See [core.k](execution/core.k), lines 378–395. The signed-16-bit displacement and confirmed taken-target boundary checks remain explicit.
3. **Type-domain boundaries.** The displayed mathematical computations use signed, signed_char, unsigned, unsigned_char, and generic. The executable `numericEncoding` also admits address, Boolean, UTF, UCS, ASCII, and the four supported float formats. Float calculations are described separately in §3.5, but §3.5's statement that Boolean and string encodings are outside the type domain does not accurately describe the current acceptance of Boolean and UTF/UCS/ASCII scalar encodings. Boolean reads, integral calculations, and reinterpretation exist; Boolean `convert` remains undefined. These encodings do not imply general string-object evaluation. See [dwarf-domains.k](domains/dwarf-domains.k), lines 169–192, and [computations.k](execution/computations.k), lines 43–52.
4. **Initial stacks and completion interfaces.** §3.4 starts location evaluation from an empty stack. The artifact permits a supplied stack for simple locations, including standalone register/byte descriptions; composites require an initially empty stack and clear it at delimiters. §3.3's normal stack judgment returns the entire stack, whereas value-purpose JSON exposes its top and also retains the full stack/configuration. See [core.k](execution/core.k), lines 14–20, 399–518.
5. **Location representation and consumer work.** The paper's `value(n,b)` drops type identity and covers both stack and implicit values; source retains `value(val(N,T))` and separate `bytesValue(B)`. Paper `composite(Π)` records descriptors in bit units. Source also retains original byte/bit parameters and assembled data/masks. Consumer assembly participates in piece-commit preconditions, uses little-endian placement, and may need register-width or memory evidence. This is beyond a spelling difference. See [composition.k](execution/composition.k), lines 46–127.
6. **Input domain and decoding failures.** §3.2 uses byte positions starting at zero; the text interface accepts declared increasing mathematical offsets, including a nonzero start, without checking encoded lengths. The JSON interface requires positive A, while the byte operations that need whole-byte addresses separately check divisibility. Prefix decoding, original END boundaries, source-operand rejection, and pure structural `inputError` handling are explicit implementation conventions, not additional execution stages or a public operation error result. See [frontend.k](frontend/frontend.k), [decoding.k](frontend/decoding.k), and [normalization.k](frontend/normalization.k).
7. **Definedness beyond the displayed formulas.** Integer `abs`/`neg` reject the minimum signed value, as required by the current §3.3 representability premise. Integer `div` additionally rejects MIN/-1 quotient overflow, while §3.3's abbreviated division discussion mentions low-bit retention and zero divisors without that exclusion. Signed `mod` MIN % -1 remains defined as zero. These guards are left unchanged. See [computations.k](execution/computations.k), lines 106–149.
8. **Floating-point boundary statement.** §3.5 places noncanonical x87 encodings outside its scope. The source implements the explicit-integer-bit format but does not add a separate validator rejecting every noncanonical carrier. Support must not be read as complete behavior for those representations. See [floating.k](execution/floating.k) and [README float boundaries](README.md#explicit-base-types-and-upstream-fixtures).
9. **Fixed inputs during nested execution.** For an ordinary rule E/C stay fixed, as in the paper. Standard calls and entry-value blocks switch the active E/C and save the caller in `returnCall`/`returnEntry`. This is an implementation mechanism for operations not displayed in §3.3; root-input preservation is distinct from invariance of the active `<expr>` term at every nested step. See [core.k](execution/core.k), lines 36–86.

There is no new error-state cell, execution wrapper, generic single-step function, or naming migration in this revision. Archived experimental identities remain unchanged. For the implemented operation inventory, runtime contexts, and consumer conventions, use the [English README](README.md); the [Chinese backup](README-CN.md) preserves the earlier document verbatim.
